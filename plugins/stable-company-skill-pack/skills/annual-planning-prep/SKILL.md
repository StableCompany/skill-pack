# Annual planning prep

## Contract
- **Job:** ready the leadership team and the Integrator for annual planning, and lay out next year.
- **Reads:** `company.md` (priorities, scorecard, rhythm, their tool); `how-we-run-meetings.md`; the year's `quarterly/` folders, `meetings/` notes and check-ins; `issues.md`; their tool, read only.
- **This skill's templates:** every `templates/` path here is in this skill's own folder, beside this file, never in the user's folder. If one will not open, use the layout described here and do not mention it.
- **Asks for:** which pieces; then, as one checklist each, the year's gaps, next year's dates and closed days, and the guide's details (with, the first time, how they run annual planning).
- **Writes:** in `annual/YYYY/` (the year being planned): `leader-prep-guide.md`, `integrator-year-review.md`, `year-calendar.md`, after a yes; with the same yes, the lines for `how-we-run-meetings.md`.
- **Show me first:** each file as it will be saved (the guide: every line filled in or changed) and the exact lines for `how-we-run-meetings.md`, in one save question; replacing a file.
- **Never touches:** their tool (no writes, even by connector), `company.md`, `issues.md`, `todos.md`, `quarterly/`, `people/`, `clarity-breaks/`, `visionary/`; anything outside this folder.
- **Done looks like:** every rate and number names its source; issues that repeated are listed by the skill's own rule, with first-seen dates; working days show their math; meetings on closed days are flagged; each day of the guide adds up.
- **Next:** rock-writer uses the working days; cascade shares the plan after the session.

Version 0.2.0, 2026-10-21.

Annual planning works when the room starts from what really happened and plans against the real calendar. This skill builds three pieces. Ask which they want, unless it is clear: "The prep guide for your leadership team, your own year review, next year at a glance, or all three?" Then do only the steps for the pieces they chose.

- **The Annual Planning Prep Guide** goes to every leader about two weeks before the session: two days in order, with space to prepare. It is a two-day version of Katie Sandquist's Quarterly Planning Prep Sheet.
- **The year review** is the Integrator's own pre-work, with a source on every line. It stays with the Integrator unless they share it.
- **Next year at a glance** counts the real working days in each quarter after holidays, PTO and planning days. Katie counted these for every leader; it changes how they set rocks.

## How to ask

- End every message with at most one question, about one thing (its own details, such as by when, are fine). Never join a second question on with "and" or "also", and never send a numbered list of open decisions: each waits for its own message. When you need several answers, ask the most important one first.
- A checklist of missing facts the user can fill in one reply (this week's numbers, dates, names, how they run a meeting, a table to fill) counts as one question, with nothing after it: no question about how or in what order to answer. Flags and open decisions never go on it, such as settling a flag, approving a rewrite or choosing between two owners: raise them one per message, in order, each with your suggested fix. You may list them once first, as statements.
- In an interview, reflect each answer in one sentence that restates only what the user said, even when the answer is a list. Add no reading, label or claim of your own. Then ask the next question.
- When a write needs a yes (the Contract's Show me first line names them), first show exactly what will be written: every line you will add or change, word for word as it will read in the file, and each new file in full (for a long guide filled from a template, every line you filled in or changed). A yes given before you showed the lines ("yes, save that") is not a yes to them. Then ask one question that covers every write: "Save all of this? Yes, or tell me what to change." Save exactly what you showed, nothing more. A yes that names only some of the writes ("save both" when you showed three) covers only those; ask about the rest. If anything changes after the yes, show the changed lines and ask again.
- Offer extras, like a printable, a draft note or another skill, as a statement, never as a second question.
- Say and write only what the user said or a file says, in chat as well as in files. Copy a commitment, a quote, a name or a number exactly as it was given; an item marked done means only what its own words say happened. When a draft needs a fact you do not have (a reason, a reassurance, a decision, a capacity, a date), write a visible placeholder such as `[confirm: does their pay date change?]`, list it for the user, and never fill it in. Placeholders are only for facts no one gave you: when a step says to ask for something, ask it, and state your own proposals (a sort, a mark, a ranking) plainly as proposals.
- Keep your working notes out of the chat, from the first message to the last report (no "Let me read the template next", no "Now I'll add the line"): say what the user needs, then your one question.
- Claim only what you did. Say a file matches what you showed only after you read it back; otherwise say what you saved.

## Where the files are

- **With folder access** (the Claude desktop app's Cowork, Claude Code, Codex, ChatGPT desktop on a local folder): look for `company.md` in the working folder first, then in a subfolder named `My Integrator Folder`, then ask where the folder is. Once you find it, read its `CLAUDE.md` (beside `company.md`) before other company files. Read and write the files directly. If the folder is read-only, give the text; never say it was saved.
- **Without folder access** (claude.ai, ChatGPT on the web): when you cannot open the folder directly, ask the user to upload the files, and use the folder map from the Project instructions or the uploads. Copy each upload and add the new lines with code, so everything already in the file stays exactly as it was. Hand back the updated file as a download with its folder path. If you cannot create files (in claude.ai, file creation is off), give only the lines to add and say which heading they go under. A new file, like the year review, goes back the same way, or as one complete markdown block if you cannot create files. Never say a file was saved. Files to ask for: `company.md`, `issues.md`, `how-we-run-meetings.md`, and the year's rock reviews, issues roll-ups and weekly prep sheets if they have them.
- **Microsoft Copilot (Cowork or Chat):** read the files the user attached from OneDrive or SharePoint. For a new file, write it to your output folder with its folder path, then offer to move it into the user's folder. For a file that already exists, give the lines to add and the heading they go under, so the user can paste them in OneDrive. Never say a file is saved in the folder until you have checked it is there.
- **Their tool is the record.** For priorities, to-dos and numbers, read the tool named in `company.md` through a connector if this session has one, read only; else take one paste, export or screenshot (images are fine); else ask. Never write to the tool: list changes for the user to make by hand. Each status and number keeps its source and date.
- **No folder yet:** offer to run `integrator-folder` first. If the user would rather not, work from what they paste.

## Step 1: Name the years

Two years are in play: the one being reviewed and the one being planned. Name the folder for the year being planned: prepping in November 2026 for 2027 means `annual/2027/`. Confirm both years. If you do not know today's date for certain, ask.

## Step 2: The year review

**Gather from the folder first.**
- **Rocks done by quarter.** Quarterly folders are named for the quarter being planned, so a quarter's rock review sits in the next quarter's folder: `quarterly/2026-Q2/rock-review.md` reviews 2026-Q1. Also use the "last quarter" line in `company.md`. If their tool keeps past rocks, read them through a connector (read only) or from one export, and note the tool and the date read. The quarter still running is "in progress": use the latest status from `meetings/*-rock-check-in.md` or the newest prep sheet, with its source and date. Never call a rock done.
- **The numbers.** Only numbers the user gives or files hold. From weekly prep sheets, count for each scorecard number how many weeks are on file and how many missed the goal. Say how many weeks are on file, and use that same count everywhere you name it; a few weeks is not a trend.
- **Issues that kept coming back.** From `issues.md` (open and solved, with dates and the lines under them), `quarterly/*/issues-rollup.md`, and `meetings/` notes. Count notes only; prep sheets repeat open issues every week. An issue repeated if it came up in three or more meeting notes, stayed open across two or more quarters, or was solved and came back. Apply this rule yourself, from the files, and never ask the user whether to count repeats. List each one with its first-seen date, which part of the rule it meets, and its source.

Tell the user in a few lines what is on file and what is missing. Then ask once for the gaps, as one checklist, and accept a paste: quarters with no record (a rock sheet, done and not done per rock, or just "3 of 4"), what got in the way of the rocks that slipped, and any numbers for the year they want in.

**Write it** from `templates/integrator-year-review.md`: completion per quarter as done ÷ total with the math and the source ("no record" where there is none); the year line from the quarters on file, named; rocks that slipped, with what got in the way in their words; the numbers, each with its source or "you said, YYYY-MM-DD"; issues that kept coming back, each with its first-seen date, the rule it meets and its source; up to three lines on what stands out, each pointing to a row above; questions to settle before the session.

## Step 3: Next year at a glance

**Collect in one message.** Show the rhythm you found in `company.md` and `how-we-run-meetings.md` (weekly meeting, same-page meeting, one-on-ones, quarterly and annual planning, department and board meetings) and ask them to confirm or correct it. In the same message, ask for next year's planning dates, the days they are closed, PTO they know of (who and dates), and big events (peak season, trade shows, launches, audits, year end).
- **Closed days:** never assume. Offer to list the public holidays for their country and year, with dates, so they can mark the ones they close for. When one falls on a weekend, use the weekday they say they observe.
- **Planning dates:** use the dates they give. A date not set yet stays `date?`.

**Work it out.**
- List each planning day and same-page meeting by date. The weekly meeting is a rule ("Mondays 9:00") plus every date it lands on a closed day.
- **Working days per quarter:** weekdays, minus closed days that fall on weekdays, minus company-wide planning days. Show the math. Then each person's working days, minus their PTO. If you can run code, count with code and show the inputs.
- **Flags,** each stated as a question to check, never as a rule: a meeting on a closed day; a planning day on a closed day or during a leader's PTO; a meeting during the PTO of the person who runs it; a planning day on top of a big event; a rock or milestone for next year in `quarterly/` due on a closed day.

**Write it** from `templates/year-calendar.md`, flags first.

## Step 4: The leadership team's prep guide

First run **Match how they run it** (below). Then fill `templates/annual-planning-prep-guide.md`. Show one checklist of what the guide needs, filled from the folder where you can, and ask them to fill the gaps in one reply:
1. Company name for the cover.
2. The year reviewed and the year planned.
3. Both dates, start and end times, and the location.
4. The length of each day. Each day's segment times must add up to its length; the template shows two 7-hour days, and IDS on day two takes what is left.
5. Where the V/TO, rocks and scorecard live (from `company.md`), for the "Before you arrive" note.
6. Who arranges lunch.
7. A numbers hint for the look back, drafted from their scorecard and industry, for them to confirm.
8. Their name for the footer.

If something in the folder may clash with their dates (a meeting already booked that day), put it on the checklist as a question, never as a rule they must follow.

Defaults, from Katie's quarterly guide. Keep them unless they ask to change them:
- **Leave the rocks-by-quarter table blank** for each leader to fill. The Integrator brings the year review to the room.
- **Rock ideas only.** SMART wording and owners are set in the room.
- **Keep the "In the room" blocks.** They tell each leader what will happen, so the prep makes sense.
- **Print-friendly,** and "Before you arrive" fits on one printed page.

Replace every `<PLACEHOLDER>`; search for `<` when done, and mark any gap as an open question for them. Keep Katie's wording beyond the placeholders and what their own format calls for. Remove the HTML comment. If `company.md` says they run something other than EOS, say the guide follows the EOS annual session shape and offer to rename the segments in their words (the vision, priorities, solving issues, the plan for the year).

## Step 5: Show me first, save

Show each piece exactly as it will be saved, with its open questions: the year review and the calendar in full; for the guide, every line you filled in or changed and the day-at-a-glance totals. Add the exact lines for `how-we-run-meetings.md` if **Match how they run it** has some. If a file exists, say so; the same yes replaces it. Ask once: "Save all of this? Yes, or tell me what to change." After a yes, save each piece they chose (`leader-prep-guide.md`, `integrator-year-review.md`, `year-calendar.md`) with its header line, and the shown lines to `how-we-run-meetings.md`. Nothing else.

Then:
- Say, as statements: you can draft a short cover note to send with the guide, in their voice from `voice-profile.md` (with no profile, mention `voice-profile` once, then write plainly; it is a draft they send); and you can make the printables, the guide (each prep page starts a new page) and the Year at a Glance page, filled from the calendar.
- **Changes to make in <tool>:** if their tool or their calendar needs the new dates, list them for the user to enter by hand. You never write to either.

## Step 6: After the session

When they come back from the session:
- "Cascade this" turns the plan into a message for each audience in `cascade`. Drafts only.
- "Update my priorities" lets `integrator-folder` update `company.md`.
- `rock-writer` writes the first-quarter rocks against the calendar's working days.

## Match how they run it

The guide should follow annual planning the way this team runs it.
1. Read the `## Annual planning` section of `how-we-run-meetings.md`. If it is there, shape the guide to it without asking: their name for the session and its parts, one day or two, their order and times, segments they skip, and segments they add, in their words.
2. If it is not there, or the file does not exist yet, ask once, in your Step 4 checklist, and only when they want the guide (the year review and the calendar never need it): "Do you run annual planning the standard way, or your own way? If you have an agenda you already use, paste it or send a photo and I'll match it." If they say standard, use the template as it is.
3. Keep the parts that make the method work even when you reshape it: an honest look back at the year, a look outside (SWOT and trends), the long-range picture, a plan with numbers, first-quarter rocks with one owner each, and segment times that add up. If their way drops one, say so in one sentence and let them decide.
4. Show me first: in the Step 5 message, show the exact lines you would save under `## Annual planning` in `how-we-run-meetings.md`, using only what they said about how they run it (for example `- standard, with our implementer facilitating`, or their agenda as they gave it), never this year's dates or a detail they did not say, and save them only after the yes that covers every file, so no skill asks again. A yes they gave earlier, before they saw the lines, does not count. If the file does not exist yet, start it with the header line `> how-we-run-meetings.md: how each of our meetings really runs. Updated YYYY-MM-DD by annual-planning-prep.` and the title `# How we run our meetings`.

## Branded printables

When the user wants something to print or hand out, make it look like their company:
1. Read the **Brand** section of `company.md` (logo file, colors, fonts, footer line). If it is empty, ask once: "Want this in your company's colors and logo? Give me your website and I'll pull them." If you can read web pages, take the colors, fonts and logo from their homepage, show them, and save what they confirm to the Brand section. If they say no, use the neutral style.
2. Fill `templates/branded-page.html` with the document. Keep the structure: brand values in the `:root` block, the logo and company name in the header, the document in `<main>`, the footer line at the bottom. Point the logo at its path relative to the saved file (`../../brand/logo.png` from `annual/YYYY/`). If you can read the logo, embed it as a data URI so the file works anywhere.
3. Save it next to the markdown version with the same name and `.html`. Right after `<!doctype html>`, replace the template's comment with a one-line header: `<!-- <file name>: printable <what it is>. Written YYYY-MM-DD by the <this skill's name> skill. -->`. Tell the user to open it in a browser and print to PDF. If you can create PDF or Word files, also save a PDF or a Word copy.
4. The markdown file stays the working copy that other skills read. The branded file is for people.

## Rules

- **Never invent.** No rock statuses, completion rates, numbers, dates, holidays, events or quotes the user did not give or a file does not hold. Unknown stays a question.
- **Every line has a source:** a file path, the tool with the date it was read, or "you said" with the date.
- **Never call a rock done.** Only the files, the tool or the user can.
- **Show the math.** Completion rates and working days show what went in.
- **The guide goes to the team; the review stays with the Integrator.** Keep candid notes about people out of both.
- **Their tool is the record.** Read it, never write to it.
- **Their words.** EOS words (rocks, V/TO, 1-Year Plan, 3-Year Picture, IDS, L10) only if `company.md` says they run EOS, or the user says them first. Otherwise: priorities, the vision, the plan for the year, solving issues.
- **Plain words.** Short sentences. No em dashes or en dashes.
- **Header line.** Every file you write starts with one line: what it is, the date, and that the annual-planning-prep skill wrote it.
